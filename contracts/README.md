# LuckyDraw contracts

Foundry project implementing `docs/SPEC.md`. No deployment of these contracts exists yet on any public chain. The
first deployment target is **BSC mainnet (chain 56)**: ADR 034 records the operator's 2026-09-16 decision to go to
mainnet as an MVP with no testnet stage, so the testnet path below stays supported but is a rehearsal option, not a
gate that was passed.

## Toolchain

- Foundry 1.8.1 (`forge`, `cast`, `anvil`) installed per user at `~/.foundry/bin`. In Git Bash: `export PATH="$HOME/.foundry/bin:$PATH"`.
- `foundry.toml` pins solc 0.8.28, `evm_version = "paris"` (conservative; confirm the BSC hardfork in force before deployment per SPEC §12), via_ir with 600 optimizer runs, no metadata hash.
- Dependencies are git submodules pinned by tag: forge-std v1.9.7, OpenZeppelin Contracts v5.2.0, Chainlink contracts 1.3.0 (`@chainlink/contracts/` maps to `lib/chainlink-brownie-contracts/contracts/`).

## Layout (SPEC §12)

```

```

## Deployment (SPEC section 12 and 14: engineering ships the scripts, the operator executes them)

```bash
# Local: mocks only, no keys, no live network. Anvil's first default account is the unlocked deployer.
anvil --port 8545 --chain-id 31337 &
forge script script/DeployLocal.s.sol:DeployLocal --rpc-url http://127.0.0.1:8545 \
  --broadcast --unlocked --sender 0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266
M=../config/deployments/31337/<lowercase draw address>.json
LUCKYDRAW_MANIFEST=$M LUCKYDRAW_BROADCAST=broadcast/DeployLocal.s.sol/31337/run-latest.json \
  forge script script/Finalize.s.sol:Finalize --rpc-url http://127.0.0.1:8545   # exact deploy blocks and hashes
LUCKYDRAW_MANIFEST=$M forge script script/Verify.s.sol:Verify --rpc-url http://127.0.0.1:8545
node ../scripts/validate_config.ts
forge test --match-path "test/script/*.t.sol"
python ../scripts/test_deployment_live.py  # isolated Anvil deploy/finalize/verify and rejection regressions

# Testnet or mainnet: the operator fills in a plan and runs the same scripts with its own signer
cp script/templates/testnet.plan.example.json ../config/deployments/97/<name>.plan.json   # fill in, drop "template"
cp script/templates/mainnet.plan.example.json ../config/deployments/56/<name>.plan.json   # mainnet form; see docs/runbooks/mainnet-launch.md
LUCKYDRAW_PLAN=../config/deployments/97/<name>.plan.json forge script script/Deploy.s.sol:Deploy --rpc-url "$LUCKYDRAW_RPC_URL" --broadcast
LUCKYDRAW_MANIFEST=... forge script script/Configure.s.sol:Configure --rpc-url "$LUCKYDRAW_RPC_URL" --broadcast
LUCKYDRAW_MANIFEST=... forge script script/DeployUpkeep.s.sol:DeployUpkeep --rpc-url "$LUCKYDRAW_RPC_URL" --broadcast   # optional Automation executor

# Testnet only: the Safe web interface lists BNB Chain mainnet, not chain 97, so the single operator Safe of
# SPEC section 12.1 is created and driven from the command line against the canonical Safe v1.4.1 contracts.
SAFE_PROXY_FACTORY=... SAFE_SINGLETON=... SAFE_FALLBACK_HANDLER=... \
  forge script script/TestnetSafe.s.sol:TestnetSafe --sig "create()" --rpc-url "$LUCKYDRAW_RPC_URL" --broadcast   # before the plan
LUCKYDRAW_MANIFEST=... SEED_DEPOSIT_WEI=... \
  forge script script/TestnetSafe.s.sol:TestnetSafe --sig "ops()" --rpc-url "$LUCKYDRAW_RPC_URL" --broadcast      # after Configure, then Configure again
LUCKYDRAW_MANIFEST=... TOKEN_DEPOSIT=...   forge script script/TestnetSafe.s.sol:TestnetSafe --sig "assets()" --rpc-url "$LUCKYDRAW_RPC_URL" --broadcast   # add an asset to a handed-over deployment
```

`Verify` is read-only and exits non-zero on any mismatch. The scripts never read a key: the signer comes from
`--unlocked` (local) or the operator's own hardware or Safe flow. `Deploy` refuses a plan whose chain id is not the
connected chain, whose `environment` does not match that chain id (local is 31337, testnet 97, mainnet 56, the
validator's rule E1), that names a coordinator without `s_provingKeys(bytes32)`, or that gives any of the three
privileged roles -- `ownership.finalOwner`, `feeAccount`, `seedAccount` -- an address with no code outside `local`:
those roles are Safes outside `local` (SPEC §10.5, §12.1); on mainnet they are three separate Safes and the §10.5
drill is performed on them before deployment, and `feeAccount` is frozen into every round at
creation. `Configure` refuses a manifest whose recorded VRF coordinator, subscription id, key hash or
`maxRequestCostNative` differs from the deployed Draw's own immutables, and refuses to create a pool until the Draw
is a registered consumer and the subscription is above the low-funding threshold. Run the steps in the order deploy,
configure, finalize, verify: a script cannot see its own creation block, so `Finalize` locates the transaction hashes
in Foundry's broadcast file and takes the block from the authenticated RPC creation receipt, logging a notice when the
broadcast file disagrees (a creation re-included at another height after a reorg is recorded, not refused).
`TestnetSafe` refuses every chain but 97 (and anvil, for its tests), refuses a manifest whose three roles are not one
Safe, verifies the Safe's version, owners, threshold and module list against the chain before every run, and sends
its four owner actions through the Safe's own `execTransaction` with a pre-validated owner signature, so the operator's
ordinary `--account` or hardware flags are the whole signing flow. It writes nothing: `Configure` is run again
afterwards to record the accepted ownership and the authorized seed cap. The seed cap is per asset, because one raw
number cannot be right for two of them: `ops()` takes each asset's cap from `SEED_MAX_PER_ROUND_<SYMBOL>` if set, else
the manifest's `pool.seedAuthorizedMaxPerRound`, else the global `SEED_MAX_PER_ROUND` -- which it refuses when it
would land on more than one asset -- else that asset's `seedAmount`, and refuses any cap below `seedAmount`. For the
same reason `assets()` refuses `TOKEN_DEPOSIT` when the manifest names more than one non-native asset. Mainnet Safes are three distinct 2-of-3
Safes created and operated in the Safe interface (SPEC §10.5).
`Verify` independently checks those receipts, exact deployment blocks and the history scan lower bound. Both require
`--rpc-url`; missing receipts and unfinalized manifests fail, even locally. The in-process tests inject labeled
synthetic RPC responses, while `test_deployment_live.py` exercises real Anvil receipts and removes its Anvil process
on exit. Its manifests and logs live under `contracts/test/script/tmp/`, leaving the checked-in records untouched.

## The Automation upkeep (SPEC §10.3, ADR 039)

`src/LuckyDrawUpkeep.sol` is a third executor beside the operator keeper and the manual path. It exists for one
failure: the single keeper host being down, rebooting or out of gas when a cutoff passes, which costs a round its
draw. It is not a replacement for the keeper and no deployment depends on it.

What it is: an `AutomationCompatibleInterface` implementation with an immutable `DRAW`, **no owner, no funds, no
`receive`/`fallback`, no setter and no storage at all**. `performUpkeep` dispatches over a four-member enum onto
`closeRound`, `requestDraw`, `expireUnrequested` and `settle` — four methods that are already public to every
address (SPEC §8.1) — and nothing else. `seedRound` and `claimRefund` are deliberately absent: one spends the seed
account's balance (§5.4), the other credits a named buyer (D9). The Draw is unchanged by any of this.

`checkUpkeep` is a `view` bounded by constants rather than by chain state. One call reads the current round of every
`Kind` of `POOLS_PER_CHECK` (4) pools — 28 rounds — then `ROUNDS_PER_CHECK` (96) round identifiers, newest first.
The second phase is not redundant: `closeRound` advances `current` in the same transaction, so a round that still
needs a request, an expiry or a settlement is named by no pool pointer — the same gap `keeper/src/keeper.ts` covers
with its own discovery scan.

Those two numbers are a gas budget, and the budget is a correctness requirement. Chainlink publishes a 10,000,000
`checkGasLimit` for chains 56 and 97, and a `checkUpkeep` over it is not an error the registry reports — it records
nothing due, and the upkeep goes quiet. Measured against the production Draw with cold storage
(`LuckyDrawUpkeepGasTest`): 1,743,623 gas for the 28 current rounds, 5,333,673 for the 96 identifiers (55,559 each),
7,077,296 together in the worst case, against a stated budget of 8,000,000 — 20% under the limit.

Coverage is complete rather than recent, because with empty `checkData` both page indices rotate with the block
number: `(block.number / ROTATE_BLOCKS) % pageCount`, `ROTATE_BLOCKS` being 20, about a minute per page at BSC's
3-second blocks. Every pool and every round identifier is therefore reached within
`ceil(roundCount / 96) × 20 × 3` seconds — about 11 minutes at 1,000 rounds. A fixed newest-first window would
instead starve every older unresolved round forever, and sooner the larger the deployment: round ids are one dense
global sequence across every pool and kind. An explicit `abi.encode(poolCursor, poolLimit, roundCursor, roundLimit)`
pins one page and does not rotate, which is the override for a second registration nailed to a slice
(`docs/runbooks/testnet-launch.md` §4b says when to want one).

`performUpkeep` re-reads the round and reverts `WrongState` if the suggested action is
no longer the one that state calls for; it revalidates state only, so a VRF subscription that drained between the
simulation and inclusion surfaces as the Draw's own `SubscriptionUnderfunded`.

Deploying it is its own script, run against an existing manifest and safe after the Safe handover, because there is
no role to grant:

```bash
LUCKYDRAW_MANIFEST=../config/deployments/97/<lowercase draw address>.json   forge script script/DeployUpkeep.s.sol:DeployUpkeep --rpc-url "$LUCKYDRAW_RPC_URL" --broadcast
```

It refuses a manifest whose chain id, `environment` (rule E1: local 31337, testnet 97, mainnet 56) or Draw code hash
disagrees with the connected chain, refuses a non-local manifest that references a mock, and refuses to run twice. It
writes `contracts.upkeep` into the manifest — address, code hash, deploy block, deploy transaction and the bound
Draw — and leaves `registry` and `upkeepId` empty. `Verify` checks the record when it is present and prints a notice
when it is absent; a manifest with no upkeep is a valid manifest.

**Registration and funding are operator steps and are not in this repository.** In the Chainlink Automation app
(`automation.chain.link`) the operator registers a **custom logic** upkeep against the deployed address, with a gas
limit sized for one action (500,000 is comfortable; `performUpkeep` performs exactly one) and empty check data, and
funds it with **LINK** — a balance entirely separate from the Draw's native-billed VRF subscription. The Automation
**registry address for the target chain must be looked up by the operator** in Chainlink's own documentation
(`docs.chain.link`, Automation → Supported Networks) and recorded in `contracts.upkeep.registry` together with the
registry's `upkeepId`; nothing here guesses it, and validator rule `D28` requires both fields or neither. The full
walk-through is `docs/runbooks/testnet-launch.md` §4b.

Running the keeper and the upkeep at once is intended. They race, the loser reverts with a named error, and the cost
is gas. Seeing the upkeep perform *every* action means the keeper is not running.

## Static analysis (Slither)

`slither.config.json` is the pinned configuration. Slither needs its own `solc`, so install the version
`foundry.toml` pins and run it from `contracts/` with its own build directories, never the ones a parallel
`forge test` is using (Slither runs `forge clean` first, and it would delete them):

```bash
pip install slither-analyzer==0.11.6 solc-select==1.2.0
solc-select install 0.8.28 && solc-select use 0.8.28
FOUNDRY_OUT=out/slither FOUNDRY_CACHE_PATH=cache/slither \
  slither . --config-file slither.config.json --json out/slither/report.json
```

`filter_paths` drops `lib/`, `test/` and `script/`, so the findings are about `src/` only. The last line of a run
reads `. analyzed (24 contracts with 102 detectors), N result(s) found`.

**Read the log before the findings.** Slither 0.11.6 cannot resolve `import {Name as Alias}` for a custom error: it
prints `ERROR:ContractSolcParsing: Missing function Variable not found: <Alias>()` and then drops the enclosing
functions from its analysis. The result is not a smaller finding set but a *wrong* one — live state variables are
reported as never used or constant, and the reentrancy and complexity findings that the same code produces once the
alias is gone never appear at all. **A run that logs `ERROR:ContractSolcParsing` is not evidence.** The CI job greps
for that line and fails on it; keep that guard. No file under `src/` imports a custom error under an alias any more
(the last two, in `LuckyDraw.sol` and `LuckyVault.sol`, were dropped on 2026-09-18), so the CI run is taken on the
real tree and is the authoritative one; `docs/REVIEW.md` records the 2026-09-16 triage that a scratch alias-free
copy had to stand in for. Do not reintroduce an alias: prefer renaming the error in `src/Errors.sol`.

Triage procedure, per finding, recorded in the newest `docs/REVIEW.md` section and nowhere else:

1. Reproduce it in the source before writing anything about it: open the cited lines and follow the call graph the
   detector claims. Several detectors do not follow private helpers or `immutable` callees.
2. Classify it as exactly one of **fixed** (with the commit and the regression test), **false positive** (with the
   reason the detector is wrong *about this code*, not a general remark about the detector), or **accepted** (with a
   named owner and what would change the decision). Nothing is left unclassified.
3. Never silence a detector to make a finding go away. Adding a name to `detectors_to_exclude` requires a one-line
   reason appended to the `_comment` block in `slither.config.json` *and* the matching REVIEW.md entry; per-finding
   triage is always preferred.
4. When the Slither pin moves, re-triage in the same commit. Findings change between versions.

`fail_on` is `none` and the CI job is `continue-on-error` until every Medium finding in the triage is fixed or
accepted with a named owner. Both come off together, before the operator signs `Deploy` for mainnet (SPEC §14).

## Rules

- Spec first: if code and spec disagree, resolve the design and update both (`CLAUDE.md`).
- Mocks are labeled and live only under `test/mocks`; a production manifest may reference none of them. The rule is
  enforced by deployed code, not by the document's own `isMock`/`feedIsMock`/`coordinatorIsMock` flags: `Deploy`,
  `Configure` and `Verify` compare every recorded coordinator, feed and asset address with the mocks' runtime code,
  so clearing the labels changes nothing.
- Never put keys, seed phrases or RPC secrets in this repository.
