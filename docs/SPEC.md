# LuckyDraw — Engineering specification v8

Updated 2026-09-16. Status: implementation baseline for local development and the private mainnet shakedown of ADR 034. Mainnet release requires the evidence in §14; no implementation or audit is claimed by this document.

Players deposit into a Vault balance, enter an asset-specific draw, and receive winnings or refunds as balance credits. The entry fee is 3%; deposits, withdrawals and payout credits have no platform fee. This specification resolves the earlier pricing, odds, fee, refund and scheduling questions. Engineering choices made to complete the design are recorded in §13.

`SPEC.md` is authoritative. `SPEC.html` is generated from it. §12.1 separates v1 build work from mainnet gates; §17 lists deferred features and commits to nothing. `ACCEPTANCE.md` maps requirements to release evidence; `spec_reference.py` checks mathematical examples without claiming to test contracts. MUST means required; MAY means optional. Earlier spec versions have been removed; `REVIEW.md` keeps the historical findings.

## 1. Product contract

| ID | Requirement |
|---|---|
| P1 | Launch on BNB Smart Chain (56), develop against a local chain; BSC testnet (97) stays supported by the scripts, schemas and configuration but is not a release stage (ADR 034). Chain ID is part of every asset, deployment and cache key. |
| P2 | One asset per pool; each pool has seven concurrent round sequences, each with a whole-USD target and a latest fixed UTC cutoff: three daily (defaults USD 100, 1,000 and 10,000 within the day), three weekly (USD 1,000, 10,000 and 100,000 within the week) and one monthly (USD 100,000 within the calendar month). A round ends at the first of: the player purchase that lifts the pot's reference value to the target with at least two distinct addresses, or its cutoff. |
| P3 | Each player purchase has a gross reference-USD value of at least USD 1 at execution under §3 (operator seed entries are configured in asset units and exempt, §5.4). There is no product maximum per purchase, address or round. |
| P4 | Deduct 3% from entry amount; reserve the fee until successful settlement. USD 1 gross means approximately USD 0.97 prize contribution and USD 0.03 fee. §5 defines exact raw-unit rounding. |
| P5 | No platform charge on deposit, withdrawal, payout or refund. Users pay network gas for their transactions; an exchange may independently charge for sending assets. |
| P6 | One winner per eligible round, with chance proportional to gross units of that pool's asset entered. Multiple purchases accumulate weight. |
| P7 | Every funded pool seeds each round with a fixed operator entry (§5.4) so that a lone player always gets a draw. No player entries at cutoff: Void, and the seed is returned in the same transaction. Exactly one distinct entering address (possible only when the seed is disabled or unfunded): full refund, credited automatically. Two or more distinct addresses, the seed included: request randomness. Multiple addresses do not prove multiple people. |
| P8 | Cancellation before an accepted randomness request refunds the full gross entry, including the reserved fee. An accepted request cannot be canceled or rerolled. |
| P9 | Winnings/refunds are on-chain available-balance credits; withdrawals are separate wallet transactions. No automatic debit authorization is implied by a deposit; the sole exception is the operator's configured seed account, debited only per §5.4. |

Proposed asset lineup: native BNB and reviewed Binance-Peg USDT (BSC-USD), BTCB, ETH, SOL and XRP. Each must pass token/feed admission independently. Unsupported assets remain visibly unavailable; never invent an address/feed to fill the grid. Testnet uses labeled mock equivalents where needed. ETH on BSC is a token representation, not the Ethereum network. HYPE is excluded.

There are up to 15 current rounds, not 15 separate custody systems. Withdrawals go to the connected balance owner's address. A transfer to another wallet is performed from that wallet after withdrawal; arbitrary withdrawal recipients are out of scope.

Out of scope: other chain deployments, bridges/shared cross-chain pots, ticket transfers/resale, multiple winners, referrals, chat/comments, email custody, fiat on-ramp, yield, guaranteed returns, custom chain, gas sponsorship and application upgrades. Chain-aware interfaces permit future deployments without promising shared balances.

## 2. Architecture and trust boundaries

```text
React pages -> typed RPC reads / event index -> BSC
React pages -> wallet transaction service --> LuckyVault / LuckyDraw
Keeper ------------------------------------> public Draw methods
LuckyDraw ---------------------------------> LuckyVault (registerRound/lock/release only)
LuckyDraw -> PriceReader -------------------> configured feed proxy (read only)
LuckyDraw <-> ImmutableVRFConsumer ----------> fixed VRF coordinator
Event indexer -----------------------------> confirmed logs + block hashes
```

| Module | Owns | Must not do |
|---|---|---|
| LuckyVault | Asset custody, available balances, registered round escrow and totals | Choose winners, read prices, make oracle requests |
| LuckyDraw | Pool config, frozen round terms, entry ranges, lifecycle, fee math | Transfer external assets or take arbitrary operator instructions |
| PriceReader library | Read/validate feed; calculate minimum raw amount | Supply owner-chosen fallback prices |
| Schedule library | UTC schedule formula | Accept caller-supplied cutoff dates |
| ImmutableVRFConsumer base | Immutable coordinator authentication and callback dispatch | Expose a coordinator setter or manual word injection |
| Web read/write adapters | Read snapshots; prepare and track signed transactions | Hold keys or claim cached data is authoritative |
| Indexer / query API | Search, history, charts, holder aggregates | Authorize purchases or determine money owed |
| Keeper | Public close/request/expire/settle calls and alerts | Privileged access to funds/outcomes |

Draw is trusted to initiate correct user debits. Separating it from Vault does not make a faulty Draw harmless; review both together. Vault binds exactly one Draw permanently. No proxy, delegatecall, arbitrary execution, owner seizure, sweep, interest-bearing strategy or automatic fund migration is permitted.

On-chain storage is authoritative. A failed indexer must not prevent direct reads, withdrawal, refund or public lifecycle calls. The production app includes a read-only index service for complete history; the static client retains direct RPC functionality during service failure. In production the static client is published by CI to a content-delivery static host with an IPFS pin as a mirror, so compromise of the application VM alone cannot replace the production static files; served JavaScript and wallet prompts remain part of the signing trust boundary; the operator VM runs only the indexer with its read-only API, the keeper and staging (§10.3, ADR 025).

All components, dependencies and generated ABIs are pinned for a release. Owner authority uses two-step transfer; final owner is an operator-controlled multisig. Keeper and indexer require no owner key.

## 3. Asset admission and the USD 1 minimum

### 3.1 Admission record

Vault keeps immutable asset identity/decimals and a mutable depositsEnabled flag. Draw pool configuration contains an immutable asset and a next-round PricingConfig (feed proxy, feed decimals, maximum age, reference kind and aggregator answer bounds; struct in §5.1). Feed changes affect newly opened rounds only; existing rounds keep their frozen copy.

Admit only exact-transfer, non-rebasing ERC-20s with 0–18 decimals and callable balance/transfer APIs; native BNB uses 18 decimals. Review issuer/upgrade/freeze powers. Deposit checks exact receipt; withdrawal checks exact Vault debit and recipient receipt for ERC-20s, reverting the transaction if deltas differ. These checks reject taxed behavior but cannot undo an issuer freeze, rebase, seizure, depeg or later malicious upgrade. Disabling deposits never removes balances or blocks withdrawal attempts.

Use a Chainlink AggregatorV3-compatible official feed proxy for reference USD valuation. Verify chain, quote direction, decimals, heartbeat, status and asset association at deployment. Prefer a feed for the exact wrapped token. An underlying-asset USD feed is allowed only with `referenceKind = UnderlyingAsset` on-chain, a recorded peg assumption in the deployment manifest and a visible label such as “USD estimate uses ETH reference price; Binance-Peg ETH can trade differently.” The manifest supplies the wording; the frozen enum tells the app and Verify page that the label is mandatory. USD 1 is defined by that disclosed reference, not guaranteed realizable sale value. Chainlink describes this wrapped/underlying distinction. [Feed selection](https://docs.chain.link/data-feeds/selecting-data-feeds).

No suitable reference feed: do not enable that asset. For each approved feed with heartbeat H seconds, set maxPriceAge = max(2H, 3600) seconds (inclusive), record H and its verification source/date, and reject configurations outside 60–172,800 seconds. The reference price gates only the USD 1 minimum, so an hour of tolerance cannot create a payout error, while it prevents transient PriceStale reverts when a 27-second-heartbeat feed posts late (ADR 020). A feed whose heartbeat cannot fit this policy is ineligible for v1. Operators monitor PriceStale reverts per pool and record each feed's observed p99.9 update interval in §15. Feed decimals must be 0–18 and remain equal to the frozen value when read. Record the aggregator's minAnswer/maxAnswer circuit-breaker bounds, or confirm that none exist, in both the price record and the PricingConfig; an answer clamped at a bound is not a market price (LUNA/USD on BSC sat at its floor in 2022).

### 3.2 Exact purchase validation

Read latestRoundData at buy execution. Require a successful call, roundId > 0, answer p > 0, and `0 < updatedAt <= block.timestamp`, with `block.timestamp - updatedAt <= maxPriceAge`. A changed decimal count or invalid/stale answer blocks only new entries; deposits, withdrawals, close, randomness, settlement and refunds do not require a price. No stale-price/manual-price fallback. Read `decimals()` and `latestRoundData()` through try/catch: a reverting call maps to PriceUnavailable; roundId==0, p<=0, updatedAt==0 or updatedAt>block.timestamp to PriceInvalid; block.timestamp-updatedAt>maxPriceAge to PriceStale; an answer at or beyond a nonzero frozen minAnswer or maxAnswer to PriceInvalid; a `decimals()` result different from the frozen feedDecimals to PriceDecimalsChanged. The API provides these fields; `answeredInRound` is deprecated and is not used as the freshness check. [Feed API](https://docs.chain.link/data-feeds/api-reference).

For token decimals d and feed decimals f:

```text
scale       = 10^(d + f)                 // exponent <= 36
minGrossRaw = ceil(scale / p)            // USD 1 threshold, rounded up
accept      = grossRaw >= minGrossRaw
usdValue(G) = floor(G * p / scale)       // whole USD, rounded down, full-precision mulDiv
targetHit   = playerCountAfter >= 2 && usdValue(grossTotal + grossRaw) >= targetUsd
              // playerCountAfter counts this buyer; the operator seed counts as one address
```

Use integer ceil division without overflowing addition. Validate the feed once per buy and emit feed round, answer and timestamp with the entry. This quote determines minimum admission and, from the same observation, whether the purchase reaches the round's whole-USD target (§6.1). It never changes weights already bought, pot asset units, or payouts; a wrong price can only advance or delay a close. Recheck at execution even if a UI preview passed. Below-minimum rejection must display the new minimum and preserve input.

Example: d=18, f=8, p=600×10^8 gives minimum 1,666,666,666,666,667 wei. One raw unit less fails. The same price values a pot of 1,666,666,666,666,666,667 wei at USD 1,000, so that is the smallest pot that reaches a USD 1,000 target; one raw unit less values at USD 999. A later price decline changes future entry minimums, never existing ownership.

## 4. Vault ledger and contract

### 4.1 Storage and deployment binding

```solidity
struct Escrow { address asset; uint256 amount; uint64 closesAt; bool registered; bool closed; bool released; }
mapping(address user => mapping(address asset => uint256)) balances;
mapping(address asset => uint256) totalAvailable;
mapping(address asset => uint256) totalEscrow;
mapping(uint256 roundId => Escrow) escrows;
mapping(uint256 roundId => mapping(address user => uint256)) lockedBy;
mapping(uint256 roundId => mapping(address user => uint256)) refundedTo;
mapping(address account => mapping(address asset => uint256)) seedMaxPerRound; // set by the account itself, per asset in that asset's raw units; 0 = no consent
mapping(uint256 roundId => mapping(address account => uint256)) seedLocked;
mapping(address asset => AssetRecord) assets;
address draw; // assigned once, no replacement
bool depositsPaused;
```

AssetRecord contains listed, tokenDecimals and depositsEnabled. IDs start at one. `setDraw` requires owner, nonzero code address and draw==0. Verify intended bytecode and Draw.vault before enabling deposits or creating rounds. Both owner transfers must be accepted by the configured multisig before deployment acceptance.

Direct token donations and forced BNB transfers create surplus without user credits. Reject ordinary BNB sends outside depositNative where possible; no sweep exists. No external-transfer path exists except withdraw. A rejected native recipient retains its balance; caller-only routing requires contract-wallet recipients to accept BNB.

### 4.2 Write interface

| Signature | Guards and effect |
|---|---|
| `depositNative()` payable | Bound Draw; native listed/enabled; not depositsPaused; msg.value>0. Credit full value to caller. |
| `deposit(address asset,uint256 amount)` | ERC-20 listed/enabled, bound, not paused, amount>0; the native sentinel reverts InvalidAsset here, and `withdraw` routes it to the native path explicitly. Safe transferFrom; receipt delta must equal amount; credit full amount. |
| `withdraw(address asset,uint256 amount)` | Listed, amount>0, sufficient caller balance; no pause/price/round gate. Debit then transfer to caller; enforce exact token deltas; failure rolls back. |
| `registerRound(uint256 id,address asset,uint64 closesAt)` | Draw only; unused nonzero ID, listed asset, closesAt>now. Register zero escrow with its cutoff, independent of deposit enablement. |
| `lock(uint256 id,address buyer,uint256 amount)` | Draw only; registered, now<closesAt, not closed, no release yet, buyer nonzero with seedMaxPerRound[buyer][escrow.asset]==0, amount>0, sufficient available funds. Move full gross entry to round escrow and add it to lockedBy[id][buyer]. |
| `authorizeSeed(address asset,uint256 maxPerRound)` | Called by the account itself (the seed Safe's own transaction); the asset must be listed or it reverts InvalidAsset. Sets the most any single round in that asset may take from it, in that asset's raw units; 0 revokes that asset alone. While the cap for an asset is nonzero the account cannot be debited through `lock` in that asset at all, and a cap on one asset never grants consent in another. |
| `lockSeed(uint256 id,address account,uint256 amount)` | Draw only; registered, now<closesAt, not closed, no release yet, 0<amount<=seedMaxPerRound[account][escrow.asset], seedLocked[id][account]==0, sufficient available funds. Move amount to escrow, record seedLocked and lockedBy. |
| `closeEscrow(uint256 id)` | Draw only; registered and not yet closed. Marks the round closed so no later lock is possible even before closesAt; called by every closing branch of Draw, including a target close. |
| `release(uint256 id,address recipient,uint256 amount,ReleaseReason reason)` | Draw only; registered, recipient nonzero and neither the Vault nor the Draw, amount>0 and <=escrow; for reason Refund also refundedTo[id][recipient]+amount<=lockedBy[id][recipient]. Marks the round released and moves escrow to available balance; no asset call. Draw skips zero releases. |

Every mutation uses a common Vault reentrancy guard, including lock/release/admin entry points reachable during asset callbacks. Vault error names where §8.1 leaves a choice: deposit before Draw is bound reverts WrongState; lock at or after closesAt reverts EntryWindowClosed and after closeEscrow or a release reverts EscrowClosed; registerRound with closesAt<=now reverts InvalidConfig; release above the round's escrow reverts InsufficientBalance. Transfer methods use checks-effects-interactions where possible; deposit measures delta while holding the guard. Reverting nested attempts cannot partially update either contract. Draw's mutations, including the authenticated callback, share one Draw guard; the callback makes no external calls, so the guard never blocks asynchronous delivery.

### 4.3 Conservation

For each asset let B=actual balance, A=totalAvailable, E=totalEscrow. Buying locks gross, including the fee reserve. There is no second committed counter in Draw; Draw holds game totals that reconcile to Vault.

| Operation x | Delta B | Delta A | Delta E |
|---|---|---|---|
| Deposit | +x | +x | 0 |
| Withdraw | -x | -x | 0 |
| Gross buy | 0 | -x | +x |
| Payout, earned fee, or gross refund | 0 | +x | -x |

- **V1:** B >= A+E under admitted-token behavior; unexpected external asset loss is an incident, not a balanced ledger correction.
- **V2:** A equals summed user balances; E equals summed registered escrows. Releases cannot spend another round's escrow.
- **V3:** Application pause/price/round state never gates available withdrawal; failed transfers leave accounting unchanged.
- **V4:** Only withdrawal transfers assets out; the recipient is always its caller.
- **V5:** Vault enforces per-round limits independent of Draw: no lock at or after the round's closesAt, after closeEscrow or after its first release; no Refund release beyond what that recipient locked in that round; seed debits only through lockSeed for an account that authorized a per-round cap in its own transaction, within that cap, once per round; and an account with an active seed authorization is never debited through the player path. A faulty Draw can still misdirect Prize or Fee releases within one round's escrow and can still debit an ordinary player wrongly through `lock` (the documented trust boundary, §11.3); it cannot lock late funds, reopen a finished round, over-refund, or touch a seed Safe beyond its cap.

## 5. Entries, ownership and fee arithmetic

### 5.1 Data model

Use uint256 for amounts, cumulative weight, counts and IDs; uint64 for timestamps after checked conversion. No artificial uint96 entry bound. uint256 overflow still reverts; no user-facing “unlimited” claim overrides machine arithmetic. No configurable max entry, pot, address share or range count exists.

```solidity
enum Kind { Day100, Day1k, Day10k, Week1k, Week10k, Week100k, Month100k } // seven sequences per pool
enum Cadence { Day, Week, Month }  // Kinds.cadenceOf(kind) picks the cutoff formula of section 6.1
enum State { Open, AwaitingRequest, Drawing, Ready, Settled, Refunding, Void }
enum ReleaseReason { Prize, Fee, Refund }
enum RefundReason { InsufficientPlayers, RequestDeadlineExpired }
enum SeedSkipReason { NotConfigured, NotAuthorized, InsufficientSeedBalance, NotOpen }
enum CloseReason { Cutoff, TargetReached }
enum ReferenceKind { ExactToken, UnderlyingAsset }
enum CallbackIgnoreReason { UnknownRequest, DuplicateOrWrongState, Malformed }
enum QuoteReason { None, InvalidRound, EntryWindowClosed, InvalidAmount,
    BuysPaused, PriceUnavailable, PriceInvalid, PriceStale, PriceDecimalsChanged,
    BelowMinimum, InsufficientBalance, SeedAccountCannotBuy, ArithmeticOverflow } // append-only ABI values; check precedence below
struct PricingConfig { address feed; uint8 feedDecimals; uint32 maxPriceAge; ReferenceKind referenceKind;
    int256 minAnswer; int256 maxAnswer; } // fixed size, no strings; bounds zero when the aggregator has none
struct Range { address buyer; uint256 cumulativeGross; } // two slots
// Draw immutables: vault, coordinator, subscriptionId, keyHash,
// requestConfirmations, callbackGasLimit (§7.1). Owner-mutable: feeAccount, seedAccount, buysPaused.
// Pool: id, immutable asset, enabled, buysPaused, next PricingConfig, seedAmount (0 = no seed),
// targetUsd[kind] in whole USD, one entry per Kind (defaults 100 / 1,000 / 10,000 / 1,000 / 10,000 /
// 100,000 / 100,000, from Kinds.defaultTargetUsd).
// Round fixed: id, poolId, kind, sequence, asset, tokenDecimals,
// PricingConfig, feeAccount, opensAt, closesAt, targetUsd.
// Round evolving: state, grossTotal, feeReserved, prizePot, playerCount, seeded,
// seedAccount (the account that seeded this round), seedGross, closedAt, closeReason,
// requestDeadline, requestId, requestedAt,
// word0, word1, winningIndex, winner, settledAt, refundedGross, refundReason, ranges[].
// Per-round mappings: grossByUser[address], refunded[address].
// Draw mappings: pools[id], rounds[id], current[poolId][kind],
// byRequest[requestId], lastSequence[poolId][kind].
uint16 constant FEE_BPS = 300;
uint16 constant BPS = 10000;
```

One raw asset unit entered equals one ownership-weight unit. There are no USD-denominated tickets or fixed ticket-price setter. A holder's chance is grossByUser/grossTotal. For one asset, 0.1 BNB has ten times the weight of 0.01 BNB, regardless of price at each buy. USD quotes validate minimums and help display; they do not normalize chances across time. Separate assets never share a draw. UI calls these “entries” and “your share,” avoiding fictional $1 ticket counts.

Ranges represent `[previousCumulativeGross, cumulativeGross)`, append-only per accepted buy. Repeated buyers can own several ranges; grossByUser aggregates them. Adjacent purchases need not merge. Zero-length ranges are forbidden. Binary search returns first cumulativeGross greater than the winning index. Use overflow-safe midpoint `lo+(hi-lo)/2`.

### 5.2 Fee rounding, custody and refunds

Let G be grossTotal before a new gross entry g. Use full-precision mulDiv, rounding down:

```text
F(G)       = floor(G * 300 / 10000)
feeDelta   = F(G+g) - F(G)
netDelta   = g - feeDelta
grossTotal = G+g
feeReserved= F(G+g)
prizePot   = grossTotal-feeReserved
```

Compute fee on cumulative round gross. Thus splitting an amount into many buys or wallets cannot reduce the round's total fee; rounding remainder of less than one raw unit remains in the prize pot. A purchase's feeDelta can differ from its isolated 3% floor by one raw unit depending on ordering. The UI quotes this and uses a minNetContribution guard; winning weight is gross and unaffected by fee rounding order. Do not multiply large uint256 amounts naively before division.

Vault locks all g. Fee reserve cannot be withdrawn or credited to the operator while Open, AwaitingRequest, Drawing or Ready. On settlement release prizePot to winner and feeReserved to the fixed feeAccount. Winner can equal feeAccount; totals still reconcile. No additional settlement or withdrawal deduction.

On Refunding, each buyer receives exactly grossByUser once, including their fee portion. Reserved fees are fully waived; no operator release occurs. Preserve original grossTotal/feeReserved/prizePot as historical amounts; refundedGross tracks released gross. No refund expiry or processing charge. Gas already spent is not reimbursed. Refunding is final for game outcome and remains claimable without an owner.

Worked example in a hypothetical 2-decimal asset with USD reference 1: entries 1.00, 2.00 and 7.00 produce gross 10.00, reserved fee 0.30 and prize 9.70; weights are 10%,20%,70%. If the first buyer wins, credit 9.70 to them and 0.30 to feeAccount. If canceled, refund 1.00/2.00/7.00 and operator earns zero. These are unit examples, not a new asset listing.

### 5.3 Purchase transaction

`buy(uint256 roundId,uint256 grossAmount,uint256 minNetContribution,uint64 deadline)` requires existing round, Open with opensAt<=now<closesAt (any other state, including a round already closed by target, reverts EntryWindowClosed; buy never reports WrongState), now<=deadline, positive gross, global/pool buying not paused, valid price and USD minimum, no active Vault seed authorization for the buyer, sufficient balance and checked additions. SeedAccountCannotBuy is checked after BelowMinimum and before InsufficientBalance in both buy and quoteBuy. Disabling future pool rounds alone does not halt an existing round's buys; buysPaused does.

Compute feeDelta/netDelta and require netDelta>=minNetContribution. Freeze price observation for the event. Update game state (append the range, add g to grossByUser, increment playerCount only when the buyer's grossByUser was zero, update grossTotal/feeReserved/prizePot) and call Vault.lock in the same guarded transaction; every effect reverts if anything fails. No wallet approval is used in buy and no allowance to Draw is ever requested. Full gross is debited from msg.sender only; the seed entry of §5.4 is the single, bounded exception. Existing terms, feeAccount and request identifiers cannot be altered by purchase. Entries are final: there is no withdrawal or reduction of an accepted entry before cutoff. After the entry is appended, if playerCount>=2 and the same fresh observation values grossTotal at or above the round's targetUsd, the transaction closes the round as TargetReached (§6.2) and advances current, leaving the successor unseeded for the keeper; quoteBuy reports this in advance and the app discloses the higher network fee. The target check runs only in player purchases, never in a seed entry.

### 5.4 Operator seed entry

A refund is the worst outcome a new platform can show a player, so every funded pool guarantees a draw. The owner points Draw at one `seedAccount` (a dedicated operator Safe holding an ordinary Vault balance; never the keeper key) and sets, per pool, a fixed `seedAmount` in raw asset units (0 disables seeding; set it well above USD 1 at configuration time, revisited by runbook). Pointing is not consent: Draw can debit that account only after the account itself has called `Vault.authorizeSeed(asset, maxPerRound)` in its own transaction, once per asset, and only up to that asset's cap per round. Consent is per asset because `seedAmount` is per pool in that pool's raw units: a single shared raw-unit cap sized for an 18-decimal asset would be unlimited consent in a low-decimal token pool, so a cap for BNB grants nothing in a 2-decimal token pool, an unlisted asset reverts InvalidAsset, and each pool's asset needs its own, separately sized decision. The account revokes an asset by setting that asset's cap to zero, and while authorized for an asset it cannot be debited through the player path in that asset at all (it remains an ordinary player in every other asset), so a compromised owner can neither point the seed at an ordinary depositor nor drain the seed Safe faster than one capped debit per round in one asset. A seedAmount above the authorized cap simply produces SeedSkipped(NotAuthorized). The keeper seeds every new round through `seedRound(roundId)` in its next cycle, so the operator pays for its own seed; Draw also attempts the seed at the first player purchase if the round is still unseeded, so no player ever faces an unseeded draw. Round creation itself does not seed: that keeps `closeRound` and a target-closing purchase within budget (measured 2026-09-11: a seed entry costs about 290,000 gas because it is a full second entry). An attempt succeeds when the round is Open before cutoff, not yet seeded, seedAmount>0 and the seed account's available balance covers it; it then behaves exactly like a purchase by seedAccount (range appended, grossByUser and playerCount updated, cumulative fee, Vault.lockSeed), records round.seedAccount and emits SeedEntered; otherwise it emits SeedSkipped with a reason and never reverts the enclosing creation or purchase. The public `seedRound` reverts instead of skipping: BuysPaused while the global or the pool's buy stop is set (a seed is a new entry, so an incident freeze stops the operator seed exactly as it stops players; the fallback attempt inside `buy` needs no separate check because `buy` itself has already reverted BuysPaused, and `quoteBuy` reports BuysPaused before it models any pending seed), and otherwise SeedNotConfigured, SeedNotAuthorized, EntryWindowClosed, InsufficientSeedBalance or AlreadySeeded.

The seed account is the only balance Draw may debit without a per-transaction signature, and only through Vault.lockSeed, within the cap the account authorized, once per round, while Open before cutoff (D9). Each round remembers the account that seeded it (round.seedAccount) and uses that account for the Void return and for outcome accounting even if the owner later points the seed elsewhere. The seed pays the same 3% fee, wins with the same probability per unit, and its outcomes are credited to seedAccount like any buyer's. It is exempt from the reference-price check because it is the operator's own money at a fixed size. A round whose only entry is the seed closes Void and returns the seed's gross in the same transaction, so empty rounds never enter Refunding. Expected value for the operator is neutral: the seed's fee returns to the treasury, and over many rounds the operator's net equals players' fees, with per-round variance bounded by seedAmount. The seed account's Vault balance is kept to a few weeks of seeds, so a Draw defect can expose at most that balance. The app labels it “Operator seed” everywhere it appears (§9), the seed account and amounts are published on Verify and in the manifest, and the §14 legal determination must cover operator participation.

## 6. UTC schedule and lifecycle

### 6.1 Calendar cutoffs

For creation time t, opensAt=t and closesAt is strictly after t:

The cutoff depends only on the kind's `Cadence` (`Kinds.cadenceOf`), never on its target tier:

| Cadence | Kinds | Formula and interpretation |
|---|---|---|
| Day | Day100, Day1k, Day10k | `(floor(t/86400)+1)*86400`: next UTC midnight. |
| Week | Week1k, Week10k, Week100k | `(floor((t+259200)/604800)+1)*604800-259200`: next Monday 00:00 UTC (ISO week; 1970-01-01 was a Thursday). |
| Month | Month100k | `nextMonthStart(t)` below: 00:00 UTC on the first day of the next calendar month. Months are 28–31 days and February follows the Gregorian leap rule. |

The Month cadence uses Howard Hinnant's public-domain civil-date algorithms (also used by BokkyPooBah's DateTime library). For t >= 0 every intermediate value is nonnegative, so unsigned arithmetic with floor division is safe. `spec_reference.py` checks them against Python's calendar for every day from 1970 to 2100.

```text
civilFromDays(z):                        // z = floor(t / 86400), days since 1970-01-01
  z   = z + 719468
  era = z / 146097
  doe = z - era*146097
  yoe = (doe - doe/1460 + doe/36524 - doe/146096) / 365
  doy = doe - (365*yoe + yoe/4 - yoe/100)
  mp  = (5*doy + 2) / 153
  m   = mp < 10 ? mp + 3 : mp - 9
  y   = yoe + era*400 + (m <= 2 ? 1 : 0)
daysFromCivil(y, m, 1):                  // first day of month (y, m)
  y   = y - (m <= 2 ? 1 : 0)
  era = y / 400
  yoe = y - era*400
  doy = (153*(m > 2 ? m - 3 : m + 9) + 2) / 5
  doe = yoe*365 + yoe/4 - yoe/100 + doy
  return era*146097 + doe - 719468
nextMonthStart(t):
  (y, m) = civilFromDays(floor(t / 86400))
  (y, m) = m == 12 ? (y + 1, 1) : (y, m + 1)
  return daysFromCivil(y, m, 1) * 86400
```

First and delayed rounds can have shorter entry windows; a monthly round opened mid-month simply closes at the next month start. At the exact cutoff an entry reverts; opening a successor selects the next cutoff. Creation never backdates availability or backfills missed rounds. Expose dates in UTC and optionally local time, labeled explicitly. Targets: each sequence also carries a whole-USD target, frozen per round and owner-settable per pool and kind for future rounds. The seven sequences and their default targets (ADR 036) are:

| Kind | Cadence | Default target (USD) | Label |
|---|---|---|---|
| Day100 | Day | 100 | USD 100 · daily |
| Day1k | Day | 1,000 | USD 1,000 · daily |
| Day10k | Day | 10,000 | USD 10,000 · daily |
| Week1k | Week | 1,000 | USD 1,000 · weekly |
| Week10k | Week | 10,000 | USD 10,000 · weekly |
| Week100k | Week | 100,000 | USD 100,000 · weekly |
| Month100k | Month | 100,000 | USD 100,000 · monthly |

A round ends at the first of a TargetReached close inside a player purchase (§5.3) or its calendar cutoff, so the cutoff is the maximum duration: a USD 100,000 round that never reaches its target still draws at the month boundary with whatever it holds, provided two addresses entered. The successor opens immediately in either case with the next calendar boundary as its own maximum; a successor opened shortly before a boundary is simply a short round. A label such as “USD 1,000 · weekly” means a target plus a latest UTC cutoff, not 24 hours, 7 days or 30 days after each user's purchase. The same target appears at two cadences (USD 1,000 daily and weekly, USD 10,000 daily and weekly, USD 100,000 weekly and monthly); those are independent sequences with independent pots and independent cutoffs.

`addPool` creates all seven first rounds, one per Kind, in enum order. “Advance current” means: set current[poolId][kind] to zero, then, if the pool is enabled, create exactly one successor (sequence=lastSequence+1, opensAt=now, closesAt from the table above, frozen copies of asset, tokenDecimals, next PricingConfig, feeAccount and targetUsd, Vault.registerRound, RoundOpened), point current at it; the keeper seeds it in its next cycle (§5.4). `closeRound` advances current atomically in every closing branch without VRF/price calls. Round creation uses validated stored configuration, never a live feed read. `ensureCurrent(poolId,kind)` rejects disabled pools, returns an existing pointer unchanged, or creates if zero. Re-enable does not create implicitly; keeper or any caller invokes ensureCurrent. Sequences increase per pool/kind even across disablement; missed periods do not create fake sequence records.

At most one Open round exists per pool/kind; it may be past cutoff and not buyable. A disabled pool's existing round finishes normally and then has zero current. Older Drawing/Ready rounds may coexist. Buying can pause between cutoff and the transaction advancing the pointer.

### 6.2 State table

All methods validate round existence, caller where relevant, state, and time. Each branch below is disjoint; zero-ticket handling takes precedence.

| From | Trigger / condition | To / effect |
|---|---|---|
| Open | `closeRound(id)`, now>=closesAt, no player entries (grossTotal==0 or grossTotal==seedGross) | Void; if seeded, release the seed's gross back to round.seedAccount as Refund in the same transaction; advance current; no request. |
| Open | `buy` by a player; afterwards playerCount>=2 and usdValue(grossTotal)>=targetUsd at that purchase's fresh price | AwaitingRequest / TargetReached; closedAt=now; requestDeadline=now+86400; advance current in the same transaction. |
| Open | `closeRound(id)`, now>=closesAt, playerCount==1 (a single player, seed absent) | Refunding / InsufficientPlayers; advance current; full refund credited by anyone. |
| Open | `closeRound(id)`, now>=closesAt, playerCount>=2, now<closesAt+86400 | AwaitingRequest / Cutoff; closedAt=now; requestDeadline=now+86400; advance current. |
| Open | `closeRound(id)`, now>=closesAt, playerCount>=2, now>=closesAt+86400 | Refunding / RequestDeadlineExpired; advance current. |
| AwaitingRequest | `requestDraw(id)`, now<requestDeadline; coordinator accepts | Drawing; record unique requestId and requestedAt. |
| AwaitingRequest | `expireUnrequested(id)`, now>=requestDeadline | Refunding / RequestDeadlineExpired. |
| Drawing | Authenticated matching two-word callback | Ready; store both words. |
| Ready | `settle(id)` by anyone | Settled; determine winner and atomically release prize and fee. |
| Refunding | `claimRefund(id,account)` by anyone for an unrefunded buyer | Stay Refunding; credit that buyer's full gross once (an account with no entry reverts InvalidAmount; a second call reverts AlreadyClaimed). |

`requestDeadline = closedAt + 86400`, set by whichever transaction closes the round into AwaitingRequest (a target close inside `buy`, or a cutoff close made less than 24 hours after closesAt), so a round that fills on day two of a month is not left waiting until month end for its refund path. A cutoff close made 24 hours or more after closesAt has no request window and goes straight to Refunding / RequestDeadlineExpired, because a round nobody closed for a day is treated as already expired. Every closing branch, including Void and Refunding, sets closedAt once, records closeReason (TargetReached or Cutoff), calls Vault.closeEscrow(id) and emits RoundClosed with requestDeadline = closedAt + 86400 so that D8 holds uniformly, although no request is possible in those states. `closeRound` before closesAt reverts RoundNotClosed; `buy` at or after closesAt, or on a round that is no longer Open because it already closed, reverts EntryWindowClosed (the closed-round case is what a purchase that loses a target race sees). At the deadline, request is forbidden and expiration allowed. requestDraw first requires that the coordinator still reports the fixed keyHash as registered (`s_provingKeys(keyHash)` exists on the v2.5 coordinator; confirm the getter against the deployed coordinator's ABI) and that the subscription's native balance is at least (pendingRequests+1) × maxRequestCostNative, reverting KeyHashUnsupported or SubscriptionUnderfunded so that a round the coordinator could never fulfil expires into refunds instead of locking; pendingRequests counts this Draw's accepted requests without a valid callback. Under its guard, requestDraw then sets Drawing before the external request, validates a nonzero unused returned ID and stores byRequest/requestId/requestedAt in the same transaction. Coordinator failure or invalid ID rolls back the entire request transaction and leaves AwaitingRequest. Exactly one successfully accepted request is allowed; reverted attempts before deadline can be retried. A request accepted before deadline remains valid afterwards.

Settled/Void never transition. Refunding never resumes entry/draw and has no claim deadline. Drawing/Ready cannot cancel or refund. No state is reset to Open. Duplicate public close/request/settle/refund transactions revert with named errors and never duplicate effects. Mark outcome/refunded before Vault releases, with rollback on failure. Claim and settle do not consult prices or owner pause flags.

## 7. Randomness, selection and failure policy

### 7.1 Request and consumer authority

Use VRF v2.5 subscription funding, native BNB billing from the operator subscription, numWords=2, requestConfirmations=200 and callbackGasLimit=300,000. Verify these against the chosen BSC coordinator at deployment; if unsupported, fail deployment and revise the configuration explicitly. The current documented BSC limits admit these values. 200 is the maximum documented confirmation count and costs roughly 150 seconds at 0.75-second blocks; it is retained deliberately for uncapped pots even though BSC finalizes in seconds (ADR 021). Confirmations reduce reorg risk but do not guarantee safety for economically unbounded pots. [Network parameters](https://docs.chain.link/vrf/v2-5/supported-networks).

Coordinator, subscription ID, key hash, confirmations and callback budget are constructor-fixed, and so is maxRequestCostNative: the lane's maximum gas price × (callbackGasLimit + coordinator verification overhead) × (1 + premium percentage) + the flat native premium, with the derivation recorded in §15. The coordinator bills at fulfilment and does not validate the key hash at request time, so the §6.2 pre-checks are the only on-chain defence against accepting a request the coordinator will never fulfil. There is no migration setter. Implement `ImmutableVRFConsumer` with an immutable coordinator address and authenticated rawFulfillRandomWords dispatch, using pinned official request interfaces/client encoding. Do not inherit an exposed mutable coordinator path. The inspected V2Plus base has a non-virtual owner/coordinator setter, so simply promising to override it is insufficient. Keep the local authentication adapter small and explicitly in audit scope. Record upstream commit and adaptation diff. [Inspected upstream base](https://raw.githubusercontent.com/smartcontractkit/chainlink-evm/793106cd598da8b2762958880300787b0b361fa1/contracts/src/v0.8/vrf/dev/VRFConsumerBaseV2Plus.sol).

The callback entry point is `rawFulfillRandomWords(uint256 requestId, uint256[] calldata randomWords)`. It authenticates the caller as the immutable coordinator, looks up byRequest, and for a known Drawing round with exactly two words stores word0/word1 and sets Ready. A zero word is valid. Authenticated unknown, duplicate or malformed callbacks emit CallbackIgnored and return without changing outcome. Unauthorized calls revert. No transfers, Vault calls, price reads, ticket search, scheduling or dynamic history loops occur. Callback guard is independent of owner pause flags. Real delivery is asynchronous; mocks must model it accordingly.

### 7.2 Weighted selection without an economic cap

The two VRF words form pseudorandom 512-bit X. With W=grossTotal>0, compute winningIndex=X mod W without constructing X in uint256:

```text
b = addmod(MAX_UINT256 % W, 1, W)       // 2^256 mod W
i = addmod(mulmod(word0, b, W), word1, W)
winner = first range whose cumulativeGross > i
```

Use EVM addmod/mulmod, not overflowing multiply/add. Under the pseudorandom-word model, modulo variation is bounded below 2^-256 for all positive uint256 W. Two words are output expansion from one request, not two independent oracle draws or 512 bits of claimed cryptographic security. This avoids the large modulo bias of a single 256-bit word when unrestricted W approaches uint256 limits. No fresh request or rejection reroll is used.

Settlement reads only fixed terms, stored words/ranges and Vault accounting. No callback order, settlement caller, timestamp, external balance or later price affects the winner. Binary search is O(log rangeCount), bounded by uint256 index width. Settlement can be retried after a reverted transaction with the same words; it cannot choose another result.

### 7.3 Availability is an explicit limitation

Chainlink advises matching request IDs, avoiding cancellation/re-request of accepted randomness and keeping fulfillment from reverting. These constraints inform this design. [VRF security](https://docs.chain.link/vrf/v2-5/security).

Before acceptance, the 24-hour deadline allows full refunds. After acceptance, no timeout refund or alternative entropy exists: seeing an unfavorable fulfillment could otherwise permit selective cancellation. If delivery never succeeds, that round's gross escrow, including its reserved fee, can remain locked indefinitely. A fulfilment that exhausts callbackGasLimit is recorded by the coordinator as failed and is never retried, with the same effect, so the measured 150,000-gas ceiling in §11.2 is a safety requirement rather than an optimization. An accepted request that is never validly fulfilled also stays counted in pendingRequests for the life of the deployment, so each permanently stuck round raises the subscription balance that requestDraw demands by one maxRequestCostNative with no on-chain clearing path; the subscription-balance alert in §10.3 counts such requests as outstanding, and the operator treats a stuck round as a permanent increase of the funding floor, not as a one-off cost. This is a design limitation, not an unresolved recovery implementation. Available balances and other rounds stay independent. The buy confirmation and Verify page disclose it in plain language.

Make-whole commitment: if a round has been in Drawing for more than 7 days, the operator reimburses every affected buyer's gross entry (fee included) by direct transfer from the treasury Safe to the buyer's address within 3 business days, records the transaction hashes on Verify, and the app shows the round as “Reimbursed by operator”. This is a voluntary payment from operator funds, not a release of the locked escrow, and it does not reopen the round. The operator maintains a published make-whole reserve in the treasury with a stated cap; Verify shows the reserve, the cap and the current sum of gross in Drawing and Ready, and the §10.3 alert table warns when that sum exceeds 80% of the reserve. Beyond the cap, reimbursement is best effort and disclosed as such.

Under healthy operation the path from cutoff to credited winnings takes about four to six minutes: one keeper cycle each for close, request and settle, 200 confirmations at roughly 150 seconds, and an oracle response within a minute. The app states “usually within about ten minutes, not guaranteed” next to the elapsed age; the operator alert ladder on the oldest Drawing age is warning at 15 minutes and critical at 60 minutes, when the operator verifies subscription funding (a top-up inside the coordinator's retry window rescues an unfunded pending request) and key status; the user-facing waiting notice starts at 24 hours (§10.3). The VRF subscription is owned by the operator multisig, never by the keeper or any hot key, with the owner transfer accepted and recorded before mainnet acceptance; cancelSubscription, removeConsumer and subscription owner transfer are prohibited for the life of the deployment except in a recorded wind-down after all pools are disabled and no round is Open, AwaitingRequest or Drawing. The configure script asserts that Draw is a registered consumer and that the subscription meets the low-funding threshold before addPool. Warn on accepted-request age >=24h, continue waiting/monitoring, and stop promising a result time. If the fixed coordinator becomes permanently unusable, disable new activity and deploy a future version for new funds; this does not recover the old pot. Mainnet risk acceptance must explicitly cover this and uncapped economic exposure.

Views: `getPool(id)`, `getRound(id)`, `getPosition(id,user)` (grossByUser, refunded flag, share numerator/denominator), `getCurrent(pool,kind)`, `getPools(cursor,limit)`, `getRanges(id,cursor,limit)`, `getRequest(requestId) returns (uint256 roundId)`, `getSeedAccount()`, Vault `getAsset(asset)`, `seedMaxPerRound(account,asset)`, balance, totals and escrow getters, Vault `getEscrow(id)`, `lockedBy`, `refundedTo` and `seedLocked` getters, and `quoteBuy(id,user,gross)` returning a `QuoteReason` (§5.1), feed observation, minGross, feeDelta, netDelta, current/post-buy ownership numerator/denominator, the pot's reference value before and after, a reachesTarget flag (which also means the purchase closes the round and, while the pool is enabled, opens the next round) and cutoff. Quote never reverts for inadmissible input and is advisory. Existing numeric reason values are preserved; SeedAccountCannotBuy and ArithmeticOverflow are appended. The seed-authorization check follows BelowMinimum and precedes InsufficientBalance. Rejected quotes return before calculating projections: feeDelta, netDelta, post-buy ownership, USD values and reachesTarget remain zero/unavailable whenever reason is not None. If an otherwise admissible gross addition or USD projection cannot fit in uint256, return ArithmeticOverflow rather than reverting or clamping the result. USD projection uses floor(gross/scale) × price + floor((gross % scale) × price / scale), with checked multiplication/addition and full-precision division. This adds no product cap; transaction execution retains its checked arithmetic. GetRound returns fixed-size summary (including seeded and seedGross) and range count, never dynamic mappings/arrays; getPool includes seedAmount. Limit 1–100; cursor>=length returns empty page and end cursor. All numeric fields and reason enums must appear in generated types.

Custom errors cover InvalidId/Kind/Config/Amount/Recipient, Unauthorized, AlreadyBound/Listed/Claimed, WrongState, EntryWindowClosed, DepositsPaused/BuysPaused, DepositsDisabled, PoolDisabled, InsufficientBalance, TransferMismatch/TransferFailed, PriceUnavailable/PriceInvalid/PriceStale/PriceDecimalsChanged, BelowMinimum, DeadlineExpired, RoundNotClosed, RequestWindowClosed/StillOpen, InvalidRequestId, KeyHashUnsupported, SubscriptionUnderfunded, InvalidAsset, SeedNotConfigured, SeedNotAuthorized, InsufficientSeedBalance, AlreadySeeded, NetContributionTooLow, and the Vault per-round limit errors EscrowClosed, RefundExceedsLocked, SeedCapExceeded, SeedAlreadyLocked and SeedAccountCannotBuy. Arithmetic overflow during execution surfaces as Solidity Panic(0x11); quoteBuy instead reports ArithmeticOverflow when a gross addition or USD projection is unrepresentable. No custom overflow error is emitted, and the client decodes Panic codes as well as Vault and Draw custom errors. No coordinator, fee or price setter exists, so none needs an error. Dependency errors may be decoded directly when documented: the compiled ABIs carry `OwnableUnauthorizedAccount(address)`, `OwnableInvalidOwner(address)`, `ReentrancyGuardReentrantCall()` and, from SafeERC20, `SafeERC20FailedOperation(address)`; each has a string catalog entry. Reverts must not be shown as raw stack traces in the app.

### 9.5 Entry flow

Enter an amount in the pool asset or as estimated USD, with quick presets (USD 1, 5, 20 and 100) converted upward to raw units. USD input converts to raw asset units using integer upward rounding from the current quote and shows the exact token debit before signing. At least USD 1 gross; no slider upper bound as a protocol limit. Max uses the available LuckyDraw balance, with no artificial product cap. The decimal text parser rejects excess precision, negatives, exponents and malformed separators without floating-point conversion.

Show before signing: gross debit, 3% reserved fee (raw precision disclosure), net addition to the prize, balance after, the user's gross share after, reference price age, UTC and local cutoff, and these facts in plain words: entries are final until cutoff and cannot be withdrawn; when the round is seeded, “the operator seed of {amount} is in this round and wins on the same odds per unit as your entry, so the draw goes ahead at cutoff”; when the pool is unseeded, “if nobody else enters, the full amount including the fee is refunded automatically”; a result is normally credited within about ten minutes after cutoff but is not guaranteed; once a randomness request is accepted the round cannot be canceled (§7.3). A new amount requires a fresh preview, and so does a new round or a new signing account: the client binds each quote to the round, the buyer and the asset it was read for and builds no calldata from a quote for anything else, because a successor round shares the pool, the asset and the cutoff calendar and would otherwise accept an entry whose disclosures belong to the round that just closed. Default deadline=min(now+300 seconds, closesAt-1); refuse if no time remains. Set minNetContribution to max(0, quotedNetDelta-1 raw unit) to tolerate only fee rounding or order movement. Minimum-USD price changes may still revert; never raise the debit automatically. The confirmation also states “This is a game of chance: if you do not win, your entry is not returned” and shows the wallet's estimated network fee converted with the reference price, labeled “network gas, not a platform fee”, with a warning when it exceeds 25% of the gross entry. In the final 120 seconds before cutoff the confirm control warns that a transaction included after cutoff reverts with nothing debited but gas spent. When the quote reports reachesTarget, the confirmation says “Your entry reaches the USD {target} target: the draw starts right after this transaction, which also opens the next round while the pool stays enabled, so the network fee is higher” and shows that estimate, including a fallback seed when this first purchase also closes the round. Always estimate the full buy calldata against current state; a gas budget from the test table is not a transaction gas limit. If another purchase reaches the target first, the transaction reverts with EntryWindowClosed and nothing is debited, and the app offers the new round. Before prompting a signature the client re-reads the feed and waits, with auto-refresh, when the price age is within 15 seconds of maxPriceAge; after a PriceStale revert it re-quotes and offers a one-tap retry with the same input.

Every share figure is labeled “current share, changes until cutoff as others enter”, and the preview shows pre- and post-entry share from quoteBuy. While the connected account is the only player, the round page and My entries say “No other player yet; the operator seed guarantees the draw” in a seeded round, or “If nobody else enters before the cutoff this round refunds your full entry automatically” in an unseeded one. Holder lists show the seed as one row labeled “Operator seed”, never as an anonymous address.

Insufficient available balance opens a top-up that preserves the intended entry. Native deposit is one transaction. ERC-20 deposit uses a TxStepper: approve the exact intended amount to the Vault, then deposit; if a nonzero allowance must be reset for token compatibility, present approve(0) and approve(amount) as explicit separate steps. No unlimited default approval and no approval to Draw. Before each ERC-20 deposit the app reads the current allowance to the Vault: if it already covers the amount, the approval step is marked done and skipped; if it is positive but short, offer approve(amount), or approve(0) then approve(amount) for tokens flagged requiresZeroReset in the asset manifest. Returning to Wallet resumes at the deposit step, shows any outstanding allowance with a Revoke control, and changing the amount re-runs the check. After a receipt is included, refetch state and price; the user confirms the entry separately. Never auto-buy into a successor or auto-sign.

Deposit success creates balance; the entry commits it; the callback changes the round to Ready; settlement credits winner and fee; the refund action credits full gross; withdrawal moves available assets to the caller. No front-end arithmetic claims a transfer occurred before a successful receipt. Gas estimate is separate from platform fees. Withdraw has no USD 1 minimum: any positive representable available amount is allowed.

### 9.6 Transaction feedback and state controls

Every transaction shows a TxStepper: Confirm in wallet → Submitted → Included → Confirmed, each step with a timestamp and explorer link; failures show the decoded custom error in plain words with a next step. The state machine is idle → preview → wallet confirmation → submitted → included → confirmed, with rejected, reverted, replaced and dropped branches. Track replacements by account and nonce; retry dropped transactions only after checking the canonical receipt and nonce; never blindly duplicate a deposit or entry. On reorg roll back confirmation and UI state and reconcile. Disconnect clears account-sensitive caches and queries but not public history; local storage contains no keys or signatures.

A `wallet-unreachable` branch covers a provider disconnect or WalletConnect session expiry while a signature is outstanding: the pending intent (type, parameters, account, chain, expected nonce, hash if known) is persisted in session storage, the user sees “Wallet disconnected before a signature was received; nothing is confirmed sent”, and on reconnect or reload the app compares the account nonce and pending transactions before offering a resend. Deep-link returns and tab restores reattach to any persisted hash and resume receipt tracking; an in-app browser without a provider gets an “open in your wallet's browser” hint.

The client asks the node for `eth_chainId` directly for the start-up assertion, writes the deployment chain id into every signing request and checks it on the response, compares the tracked receipt and transaction body with the request it prepared, requires three consecutive absent polls and a final receipt re-read before a replaced or dropped verdict, and re-reads the receipt on every poll so a reorged-out inclusion rolls back to submitted.

Buy, withdraw and claim controls act on the latest on-chain state as soon as the previous receipt is included, because the contracts re-validate every precondition; the confirmation policy in §10.1 only changes the provisional/confirmed badge, history and aggregates. Deposit success reads “Available to use now; shown as final once the chain finalizes it, usually within seconds.”

Client security: a strict Content-Security-Policy with no inline scripts and connect-src limited to the configured RPCs, index API and WalletConnect relay; all assets self-hosted or SRI-pinned; no third-party scripts on any page that can sign; the deployment manifest's code hashes are checked against the chain before any write; a decoded summary (function, round, asset, amount and, for approvals, the spender) is shown before every wallet prompt; dependencies install with `pnpm install --frozen-lockfile` and pass dependency review in CI; the build is reproducible, CI publishes a release manifest (every file with its SHA-256 plus the build hash), authenticated by a signature or independently pinned release hash outside the serving origin; Verify displays the build hash as informational, never self-authenticating; an off-host tamper canary fetches the production static origin and the staging origin every five minutes, compares the release-listed files and entry documents against that independently trusted manifest and raises a critical alert on any mismatch (§10.3). ### 9.7 Accessibility, language and content

Meet WCAG 2.2 AA: logical focus order, visible focus, labeled controls and errors, contrast per §9.3, target sizes per §9.1, reduced-motion support, and dialogs with focus trap and focus return. Announce transaction progress through a polite live region and failures through an assertive one; announce the countdown only at thresholds (one hour, ten minutes, one minute, closed), never every second. Every money action is completable with keyboard alone and with a screen reader. Content reflows without horizontal scrolling at 320 CSS px; focus indicators and non-text controls have at least 3:1 contrast and are never hidden behind sticky navigation or toasts; design tokens (color, type, spacing) live in one shared file. Run an automated accessibility audit (axe or equivalent) on every route and state in CI, and a manual keyboard and screen-reader pass before release.

English only in v1 with every string in one externalized catalog. Format numbers with `Intl.NumberFormat` and an explicit locale; numeric input accepts “.” as the only decimal separator with an inline hint; displays round debits and fees up and prizes and shares down, never show “100%” unless exact and show “<0.01%” below the floor, with full raw precision on expand; show dates as “2026-10-01 00:00 UTC (08:00 your time)” with the IANA zone named. Responsible-play content is a UI requirement subject to the §14 legal determination: an 18+ statement, “only enter what you can afford to lose”, and a help link on entry pages. Wallet activity is public on-chain. Analytics are off until the viewer opts in and never include wallet address, balances, amounts, signatures or per-account identifiers; no third-party script loads before consent except the wallet connector; index API and RPC proxy logs truncate client IP and are never joined with address-scoped queries; a Privacy section in Help names the RPC provider, WalletConnect relay and index API as parties that observe the connected address. A manifest-configured access notice component, disabled by default, can show a plain-language notice or attestation before wallet connection; its content and activation come from the operator after the §14 determination, and its presence is not a claim of compliance.

### 9.8 Metrics and activity semantics

Gross entered counts EntryBought.gross once. SeedEntered amounts are excluded from player gross, participant counts and the leaderboard and are reported separately as operator seed; the Void-round seed return emits Refunded(roundId, seedAccount, seedGross), and any Refunded or RoundSettled.prize whose recipient is that round's SeedEntered account is reported as an operator seed outcome, never as a player refund or prize. Winnings count RoundSettled.prize for winner; operator earnings count fee separately. Refunds count Refunded.gross. Period player net=prizes+refunds-gross entries whose events occurred in that UTC period, excluding deposits, withdrawals and operator earnings; label “period cash flow,” since entry/outcome can cross periods. Lifetime counts use deployment history with visible completeness. No estimated all-asset USD profit leaderboard in v1.

Charts use actual event snapshots of prizePot; holders aggregate grossByUser. Odds are current shares and can change until cutoff. History preserves asset units; current USD conversion must not be presented as historical realized USD profit. Fee reserve is never shown as withdrawable operator revenue before settlement.

## 10. Data, indexer, keeper and operations

### 10.1 Read and index contract

`packages/client` defines bigint-based Pool/Round/Position/Quote/Event types and generated ABIs; pages use adapters, never ad hoc RPC scans. Related direct reads use one blockTag; return chainId, blockNumber, blockHash, timestamp and confidence with the snapshot. Provisional values are visually distinct from confirmed ones. Display confirmation and cache keys use the RPC's `finalized` block tag where supported (BSC fast finality), falling back to `safe` and then to a 200-block depth; the tag or depth in use and the observed included-to-finalized latency are recorded in §15. This is a presentation parameter, not a promise of economic finality. Direct reads are batched through Multicall3 (canonical 0xcA11bde05977b3631167028862bE2a173976CA11 on chains 56 and 97, verified in the manifest) so one call yields one consistent block; the client refreshes snapshots at most every 4 seconds, re-quotes on debounced input (300 ms) and every 10 seconds while the entry panel is open, drives all countdowns from one 1 Hz ticker, reuses the cached snapshot when the block hash is unchanged, and stays under 30 RPC requests per minute per idle tab.

Indexer uses Node/TypeScript and PostgreSQL, scanning from verified deployment block via an operator RPC with required historical coverage. Maintain block journal and cursor transactionally. Event unique key=(chainId,txHash,logIndex), with blockHash retained. Indexer, keeper and client accept only logs whose emitter address equals the manifest Vault or Draw address for that chainId, correlate FundsLocked/EntryBought pairs by transaction hash, and ignore look-alike emitters. Sort block/transaction/log indexes. Reconcile chain hashes, roll back orphan events/derived rows to a common ancestor and replay. Deep divergence beyond the retained 2,048-block journal triggers rebuild from deployment and a degraded status. Never serve silently partial aggregates as complete. Targets: head lag p95 at most 10 seconds, warning at 60 seconds, API degraded flag at 120 seconds; ingest at `latest` and mark rows confirmed at `finalized`. raw_events and blocks are the append-only canonical source: `derive` rebuilds every derived table from them with zero RPC calls, any migration touching derived tables bumps derivationVersion and triggers re-derivation, and migrations are forward-only and applied by a single migrator before ingest starts. The initial getLogs chunk is 2,000 blocks and halves on a range refusal (a block-range or result-set cap), while a rate limit (JSON-RPC -32005, HTTP 429 or an equivalent message) leaves the chunk unchanged and retries the same range after an exponential jittered wait from 1 second to a 15-second ceiling, at most six times, because a narrower range is the same number of requests; a response whose block range or result set was silently reduced is treated as an error and re-fetched with overlap. Keeper and indexer use at least two independent RPC providers (one operator-run or paid with full log history), fail over per request on error or timeout and re-verify chainId after failover. A full rebuild of one year of history completes within 4 hours and is timed in acceptance.

Tables: deployments, blocks, raw_events, pools, rounds, entries, round_holders, account_activity, daily_asset_flows, sync_cursors. Derived tables are rebuildable. Store uint256 as decimal strings or NUMERIC(78,0), never JS number/SQL floating point. Addresses are stored lowercase with a CHECK constraint. Required indexes: raw_events UNIQUE(chain_id, tx_hash, log_index) and (chain_id, block_number, log_index); entries (chain_id, round_id, cumulative_gross); account_activity (chain_id, address, block_number DESC, log_index DESC); round_holders UNIQUE(chain_id, round_id, holder) plus (chain_id, round_id, gross DESC); rounds (chain_id, pool_id, kind, sequence); daily_asset_flows (chain_id, asset, day). API endpoints `GET /v1/status`, `/pools`, `/rounds/:id`, `/rounds/:id/entries`, `/rounds/:id/holders`, `/accounts/:address/activity`, `/accounts/:address/positions`, `/leaderboard` require chainId and deployment identity, cursor pagination (1–100), stable ordering, filters, coverage/from/to block and lag. Responses never include signing functionality. The API connects with a PostgreSQL role granted SELECT only, a statement timeout of at most 5 seconds and a bounded pool; it validates addresses as 40 hex characters (compared lowercase), IDs as decimal uint256 and cursors as signed opaque tokens, rejecting anything else with 400. Responses whose to-block is at or below the finalized block carry `Cache-Control: public, max-age=86400, immutable` and an ETag of (deploymentId, toBlockHash); head-dependent responses use max-age=5. CORS is limited to app origins; the default limit is 60 requests per minute per IP with 429 and Retry-After, leaderboard and activity endpoints weighted higher. deploymentId is `${chainId}:${lowercase Draw address}` everywhere: API, caches, keeper and manifest.

Browser caches in IndexedDB key by chain/deployment/block hash and account where relevant. Cache invalidates on reorg/config change. Direct RPC handles money views, quotes and writes even when indexer fails; indexed-only lists label unavailable/partial and link to explorer. PostgreSQL, API and nginx listen on loopback/private interfaces only; the API public edge reaches nginx through the outbound tunnel in §10.4; the connected user's balances and positions are always read from RPC, so a tampered database cannot directly change contract balances. It can still mislead a user into a harmful action; signing targets, terms and amounts must be independently verified against trusted chain state. Auto-reduce log chunk size on RPC limits, bounded retries with backoff; do not rescan genesis or every historical round on each page load. Round evidence JSON is produced by the indexer from entries (streamed, gzip) and includes the RandomnessReceived and RoundSettled fields plus keccak256 of the ordered (buyer, cumulativeGross) list, defined as the keccak256 of the concatenation, in range order, of the 64-byte `abi.encode(address buyer, uint256 cumulativeGross)` of every range with no length prefix or separator (the client's `rangeListHash` and the indexer produce the same value); the client verifies the winner by binary search over the list and spot-checks up to three random pages against getRanges, showing size and page count before download above 10,000 ranges.

### 10.2 Keeper

Dedicated low-balance operational wallet runs every 30 seconds plus an extra cycle at 00:00:01 UTC, reads the chain timestamp from `latest` (never from the display depth), discovers work from logs plus a persisted set of round IDs seen in RoundOpened that have not reached Settled or Void, keeping Refunding rounds until refundedGross equals grossTotal (each read through getRound every cycle, independent of log delivery); for a Refunding round it enumerates unrefunded buyers from its indexed EntryBought and SeedEntered logs, falling back to getRanges, and credits them across as many cycles as the 20-action budget requires, resuming after a restart with no manual claim needed, and persists its cursor and in-flight transactions. Per cycle limit 20 actions with independent transactions sent with consecutive nonces without awaiting receipts: settle Ready and expire eligible first, then credit refunds (claimRefund for every unrefunded buyer of a Refunding round), then close, ensure current, seed unseeded Open rounds and request; requestDraw is enqueued in the same cycle once the keeper's own close is mined. The keeper's buyer scan pages that log read under the §10.1 rules: a range refusal halves the window and re-reads the same start, while a rate limit leaves the window unchanged and retries the same range after an exponential jittered wait, at most six times, after which that one round's scan fails with an error naming the RPC rather than quoting it, having moved no cursor and skipped no block. Fair round-robin scheduling across pools prevents starvation. Before each send the keeper simulates the call with eth_call at `latest` and skips it on revert; a (round, action) pair that fails simulation or reverts backs off exponentially from 30 seconds to 10 minutes and raises a warning after three consecutive failures. Anyone can perform identical calls from the app.

Transactions are EIP-1559 type 2 with maxPriorityFeePerGas = max(node suggestion, configured floor) and a configured maxFeePerGas ceiling (BSC's base fee is zero, so the priority fee is the effective price and validators enforce a minimum); gasLimit = estimateGas × 1.3 capped at 600,000. A transaction not included within 60 seconds is replaced at the same nonce with a fee at least 12.5% higher up to the ceiling, then alerted. On start-up the keeper reconciles persisted in-flight hashes against receipts and the pending nonce before any send and never reuses a nonce whose outcome is unknown. Exactly one keeper instance may be active per key, enforced by a leased lock (PostgreSQL advisory lock or equivalent) with a TTL shorter than one cycle; a standby acquires the lease and completes nonce reconciliation before its first send, and losing the lease halts sending mid-cycle. Keeper state is fully reconstructible from chain (receipts, pending nonce, getRound), so its store needs no backup.

Redundancy, before mainnet: a second keeper with its own key runs on an independent host (different provider or region) and acts only when an eligible action has waited more than 120 seconds, reducing overlap with the primary without guaranteeing race-free execution; on-chain idempotency makes any overlap harmless beyond wasted gas. Before mainnet a Chainlink Automation custom-logic upkeep is registered as a third executor: a small `LuckyDrawUpkeep` contract with no funds and no privileged role, whose bounded checkUpkeep work covers both current and historical unresolved rounds and whose performUpkeep revalidates the suggested state and calls only whitelisted public Draw methods; Draw needs no change. Every keeper sends a heartbeat each cycle to an external dead-man's-switch monitor that alerts after two missed cycles, independent of the host's own alerting. Key custody: the keeper key is stored as a systemd encrypted credential bound to the host (`systemd-creds`, LoadCredentialEncrypted), isolated from other unprivileged service users and never present in the repository, environment files, shell history or the web root; the running keeper and a sufficiently privileged host attacker can access the usable key, so host binding is not protection from live root compromise; the operating balance budget is about 30 days of gas and is refilled manually on alert, never automatically; this is an operational budget, not an on-chain spending limit, and the whole hot balance may be stolen; an independent on-chain monitor alerts critically on keeper transactions outside the Draw target/selector allowlist, nonzero transferred value or abnormal gas spending; it can detect but cannot prevent theft by a compromised signer; the key holds no other role (not subscription owner, not admin, not fee account).

Healthy targets: close/request/settle attempt within two minutes of eligibility; warning after ten minutes. Confirmed final display follows chain confirmation policy. Operator funds the subscription initially with at least 30 days of forecast requests times the coordinator's maximum request cost times three, and the keeper with at least 30 days of gas, using the lowest-gas-lane key hash; low-value pots are drawn at the operator's expense and no minimum pot is silently added to avoid costs. The operations record keeps a per-round cost model (VRF verification plus callback gas at the configured lane plus the native premium; keeper gas for close, request, settle and ensure; fixed infrastructure), refreshed at each runbook review; the admin page shows 30-day actual spend against it and alerts above 150% of forecast. VRF and keeper expenses never debit Vault liabilities.

The MVP keeper of ADR 033 and ADR 034 runs a deliberately reduced single-process form of this section: one loop on one host, the §6.2 decision table over every pool, at most one transaction per round per cycle, simulate-before-send and an in-memory in-flight map. It does not provide the backup instance and its leased lock, the Automation upkeep, the complete alert table, the EIP-1559 gas policy with the 60-second same-nonce replacement, the external heartbeat, the exponential per-(round, action) back-off with the 20-action budget and round-robin scheduling, the persisted cursor and in-flight set with start-up nonce reconciliation, or the extra cycle at 00:00:01 UTC; `keeper/README.md` lists each one. All of them remain requirements of this section; ADR 034 places them after the MVP rather than before the first mainnet round, except the durability work §12.1 lists in the MVP gate: the hardened systemd unit and credential file, the heartbeat and alert webhook, the chain-id assertion and the per-draw cost meter.

### 10.3 Operations and incident response

Monitor actual custody versus liabilities, available/refund totals, subscription balance, oldest Drawing/Ready age, delayed cutoff action, RPC health, index lag/reorg, oracle staleness and PriceStale revert rate. Every alert has a severity, threshold, repeat interval and owner:

| Signal | Warning | Critical |
|---|---|---|
| Custody below liabilities for any asset at a finalized block | none | Immediately |
| Keeper action overdue | 10 min | 60 min |
| Oldest Drawing age | 15 min | 60 min: verify subscription funding and key status; 24 h starts the user-facing waiting notice; no cancellation |
| Index head lag | 300 blocks for 5 min | 2,000 blocks or journal-exceeded rebuild |
| Keeper wallet balance | under 7 days of projected gas | under 24 h |
| Subscription balance | under the low threshold (greater of 7 days of observed spend and 15 × maximum request cost) | under outstanding plus two requests, where outstanding includes every permanently stuck request (§7.3) |

| PriceStale reverts per pool | above 5 per hour | none |

Critical alerts repeat every 30 minutes until acknowledged, go to Telegram plus one independent channel, and the named on-call owner acknowledges within 30 minutes. Telegram credentials and signing keys live in operator secret storage, not source/build/browser.

Hosting: production static files are CI-built and CDN-served independently of the operator VM. The recorded Oracle Cloud ARM VM hosts API, indexer, keeper and access-protected staging only; nothing is hosted from home or office. No remote changes were made by this documentation revision.

Host hardening (patching, SSH restriction and unprivileged services before the host runs the mainnet keeper; the rest at the §12.1 gates; verified by U25–U29): OS fully patched with dnf-automatic security updates enabled; SSH key-only with password/root login and agent forwarding disabled, routed through the authenticated admin tunnel with no public port 22 (§10.4) before the host holds a mainnet keeper key; an IP-range-restricted key-only port 22 is acceptable for local and staging work; Manifests and deployment receipts are committed to the repository; prove rebuild from chain during acceptance. Published status distinguishes chain, oracle, app and index outages.

### 10.4 Operator privacy and origin isolation

Goal: avoid exposing the operator's home IP or personal location through normal visitor traffic, administration, public artifacts or a compromised app VM. The hosting provider's location is distinct from the operator's. Privacy is not a guarantee against provider records, compromised endpoints or correlation.

| Boundary | Required control | Remaining visibility |
|---|---|---|
| Public static app | Managed CDN/static origin, CI-only deployment, independent canary trust anchor | Visitors see CDN endpoints; DNS/CI/static-provider takeover can still phish signatures. |
| Public API/staging | cloudflared outbound Tunnel to loopback nginx/API; staging behind Access; no direct-origin A/AAAA or IP-encoded names | Cloudflare/provider/RPCs can observe cloud-origin egress; old DNS may reveal retired addresses. |
| Administration | Access with hardware-key MFA, explicit operator policy and separate SSH key; no public SSH; VPN active on admin device with IPv4/IPv6/DNS kill switch and no direct fallback | VPN, cloud, identity and access providers retain their own visibility; runtime endpoint compromise defeats it. |
| Database/services | Loopback/private bindings, distinct service users, least privileges, cloud and host IPv4/IPv6 ingress deny | Root can read runtime secrets/data; host-encrypted keeper key remains stealable during compromise. |
| Public records | Registrar privacy where available, accurate required registration, dedicated project contacts, metadata/EXIF review, public artifact allowlist | Legal disclosures, KYC/billing, cached artifacts and treasury history can associate an identity. |
| Logs | Separate restricted off-host security logs, redact public diagnostics/analytics, default 30-day raw-IP security retention; do not disable incident evidence | Authorized security/provider administrators may retain access under their policies. |

Cloudflare Tunnel supports outbound origin connections without public inbound ports. Require both cloud firewall and host firewall to deny direct Internet origin access, including IPv6; no leftover public 22/80/443/5432/debug exceptions. Authenticate SSH separately from the public read API. Prefer private VM interfaces with NAT egress for new infrastructure; a retained public IP must be unreachable as an origin. [Tunnel documentation](https://developers.cloudflare.com/tunnel/).

Protect the admin laptop's entire project browsing/console/SSH/wallet-RPC traffic with a fail-closed VPN, and test DNS, IPv6, browser WebRTC and drop behavior. An admin access proxy alone does not hide the client's IP from its provider. Do not forward the SSH agent or enter treasury/owner secrets on the VM. Keep independent recovery access and verify a second admin session before changing firewalls or retiring old paths.

DNS-only records, mail configuration, error headers, source maps, release archives, screenshots and public docs must not expose origin identifiers or operator personal data. Raw inventory belongs in an ignored private operations file; /.private is not encrypted and this OneDrive workspace can still sync it, so personal home IP and keys must not be stored there. Never upload the repo root as a web artifact. Scan public artifacts against private inventory without echoing matches. Public contract addresses and fee flows remain transparent.

Already published DNS/certificate/chat/Git data cannot be made undiscoverable by proxying today. Retire IP-encoded legacy hostnames and their HTTP-01 renewal dependencies after the replacement route/TLS is verified. Use new/private origin addressing if future separation is needed, with firewall isolation even if that address is learned. Do not claim removal of historical records. [Origin protection](https://developers.cloudflare.com/fundamentals/security/protect-your-origin-server/).

Network geolocation may indicate a VPN/cloud region; it is not proof of the operator's home or physical presence. Other disclosures can still identify the operator. Acceptance U30–U37 and `docs/runbooks/operator-privacy.md` cover controlled verification and lockout-safe migration. No live privacy control is marked passed solely because it is written here.

### 10.5 Signing custody and release authorization

Before mainnet, the owner, treasury and seed Safes each require 2-of-3 independently generated hardware-wallet keys. Separate seed backups physically; never put a quorum of keys or backups on one device, cloud account, password manager or recovery path. Signers verify transactions from independent devices using a trusted decoder and the written change record, including chain, Safe address, nonce, operation, target, value, calldata and refund fields. Never approve blind data. A shared workstation showing two hardware wallets the same false summary does not satisfy independent verification. Separate Safes limit accidental role mixing; overlapping signer sets still share compromise risk. Record whether distinct people control the keys; one person holding every key is not protection against that person's coercion or mistakes.

Use a pinned, verified Safe deployment with no enabled execution modules or custom guards in this baseline. Record the implementation, owners, threshold and fallback-handler code in the deployment record and monitor changes independently. Modules can bypass normal signature verification, so a threshold alone does not establish effective authority. Any extension requires a revised threat review before use. [Safe account concepts](https://docs.safe.global/advanced/smart-account-concepts).

Require a recovery drill on the mainnet Safes themselves, performed before the contracts are deployed; ADR 034 removes the testnet rehearsal, so the drill has no earlier stage to hide in. The three checks are unchanged: one unavailable signer still permits an authorized action with the other two; one compromised signer alone cannot act; remaining signers can replace a lost signer. Prove treasury withdrawal from Vault through the actual Safe and its pinned receiving configuration once the Vault exists and before any customer link is shared. Record the outcome in the release-authority record under `custody.recoveryDrill` — `performed`, `date`, `unavailableSignerPassed`, `compromisedSignerBlocked`, `signerReplacementPassed`, `treasuryWithdrawalProven`, `receiptRefs`, plus `chainId` and the `safes` the drill was performed on (owner, treasury, seed), which must equal the manifest's `finalOwner`, `feeAccount` and `seedAccount` — without recording seeds or backup locations publicly. Failed recovery or an unverified configuration blocks mainnet.

Production source, workflow and deployment-policy changes require a reviewer other than the author. Release approval binds the exact source commit, artifact digest and deployment destination; a changed digest invalidates approval. Protect deployment credentials behind a separate approval step and disable self-approval and routine administrator bypass. Use least-privilege job permissions, fresh isolated runners, lockfiles, actions pinned to full commit SHAs and short-lived deployment credentials where supported. Untrusted pull requests never execute with production secrets or write permissions. Scan dependencies, workflows, bundles and logs; resolve exploitable critical/high findings before release. [GitHub workflow security](https://docs.github.com/en/actions/reference/security/secure-use).

The deploy job promotes the approved artifact without rebuilding it. Record signed build provenance tying its digest to the approved repository, workflow, commit and builder identity; verification must check these expected identities, not merely the existence of a valid signature. Reproduce the release on an independent clean builder and explain any nondeterministic metadata before approval. The off-host canary trusts the separately approved digest; neither the publishing credential nor the app VM can update that trust record. Scope publishing credentials to the intended site, with no DNS, registrar, identity-policy or account-recovery authority. Protect recovery accounts with hardware-key MFA, separately held recovery material and off-host change alerts. Document provider-superadmin recovery powers as residual risk; workflow review cannot make a hosting-provider takeover impossible.

U38–U41 are required before mainnet. These are requirements for implementation and controlled drills, not evidence that accounts, keys or release automation are already configured. A release checklist passing is not proof that reviewed code is free of vulnerabilities.

## 11. Verification properties and acceptance evidence

### 11.1 Draw properties

- **D1:** Vault escrow equals grossTotal in Open/AwaitingRequest/Drawing/Ready; grossTotal-refundedGross in Refunding; zero in Settled/Void. Sum by asset equals Vault totalEscrow.
- **D2:** Range ends strictly increase to grossTotal; grossByUser sums to grossTotal; playerCount equals nonzero buyers; stored ranges reproduce all buyer weights.
- **D3:** feeReserved=floor(grossTotal×300/10000); prizePot=grossTotal-feeReserved; on settlement releases sum to grossTotal; on cancellation total eventual gross refunds equal grossTotal and earned fee is zero.
- **D4:** At most one Open round per pool/kind, and current is nonzero exactly when one exists. Closing/ensure cannot duplicate successors; unrelated callbacks never move current.
- **D5:** Fixed terms never change; entries stop at close (target or cutoff) and never continue past cutoff; accepted request ID/words never overwrite; settled outcome is immutable and determined only by the frozen ranges/words.
- **D6:** Admin never debits/releases or sets price answers/winners/randomness; only bound Draw moves internal money; only immutable coordinator supplies accepted words.
- **D7:** With advancing time and caller gas, Open reaches Void/Refunding/AwaitingRequest; AwaitingRequest reaches Refunding or Drawing; under valid VRF delivery Drawing reaches Ready; Ready settles without owner. Refunding buyers can claim once at any later time. No unconditional Drawing liveness claim.
- **D8:** Per pool/kind each successor has sequence=previous+1 and lastSequence is the newest; byRequest is injective with byRequest[requestId]==roundId; refundedGross equals the sum of grossByUser over refunded buyers; every round satisfies closesAt==cutoff(opensAt,kind), and once closed has closedAt set exactly once with requestDeadline==closedAt+86400.
- **D9:** Draw debits a balance without a per-transaction signature only through Vault.lockSeed, only for an account that authorized a per-round cap for that round's asset itself, only up to that cap and the configured seedAmount, at most once per round, only while Open before cutoff; round.seedAccount is the account seeded and seedGross equals that debit; a Void round returns exactly seedGross to round.seedAccount even if the owner's pointer changed; a round whose only entry is the seed never requests randomness; claimRefund credits only the named buyer and only once.
- **D10:** A TargetReached close happens only inside a player purchase whose fresh, valid price observation values grossTotal at or above the round's frozen targetUsd with playerCount>=2, closes at that transaction's timestamp before closesAt, and never from a seed entry, a stale or invalid price, or with fewer than two addresses; a round that never reaches its target closes at its cutoff exactly as before.

| Threat | Control and remaining exposure |
|---|---|

A deployment script cannot observe its own creation block: it simulates against the latest block and broadcasts afterwards, so `Deploy` records the simulation block as a lower bound and `Finalize` replaces `contracts.*.deployBlock`, `deployTx` and `chain.startBlock` with the broadcast receipts' values before the manifest is published; consumers treat `startBlock` as a scan lower bound, never as an equality. The blank operator plan lives at `contracts/script/templates/testnet.plan.example.json`, outside `config/`, because the validator rejects every template by design and CI validates the whole `config/` tree. Deployment history is verified against the connected RPC: `Finalize` uses the broadcast file only to locate the creation transaction hashes, requires successful receipts for the named Vault and Draw in canonical blocks, and records the receipts' blocks (a broadcast file whose block differs, as after a shallow reorg re-included the creation, produces a logged notice rather than a refusal). `Verify` independently repeats those receipt checks, requires exact `deployBlock` agreement, and checks `startBlock` against the receipt blocks. Missing receipts, an RPC failure or an unfinalized manifest fail verification, including on local Anvil; in-process tests supply explicitly labeled synthetic RPC responses. Both commands therefore require `--rpc-url`. Configure recovery finds sequence-1 rounds in stored history, including when current rounds have advanced, and does not derive original round IDs from current pointers. Plan/manifest rewrites preserve optional chain identity/finality, Safe records, issuer reviews and notes. The configuration validator rejects every non-object document root, including JSON `null`. `Configure` requires the manifest's VRF coordinator, subscription id, key hash and `maxRequestCostNative` to equal the deployed Draw's immutables before it opens any pool, so the subscription its readiness pre-checks examine is the one the Draw will request from. The non-local mock rule is enforced against deployed code, not the document's labels: `Deploy`, `Configure` and `Verify` compare every recorded coordinator, feed and asset address with the runtime code of `test/mocks`, and `Deploy` refuses an `environment` that disagrees with the connected chain id. Outside `local`, `Deploy` and `Verify` require deployed code at `finalOwner`, `feeAccount` and `seedAccount`, because `feeAccount` is frozen into every round at creation and an address pasted from another chain cannot be recovered. `Verify` compares the Draw's pool count with the manifest's asset count so an unrecorded pool cannot hide behind a green run.

## 17. Deferred features and extension points

Nothing here is required for v1 or scheduled; the operator decides if and when to iterate, normally after observing real customers. Each row records what the current design already allows, so a later iteration extends the system rather than redesigning it, and whether it needs a new contract deployment (there are no upgrades, ADR 008).

| Feature | Already provided by v1 | Needs a new deployment? |
|---|---|---|
| More assets | Admission process, `listAsset` and `addPool`, manifest badges | No |
| Different targets, seeds or pricing | Owner setters for future rounds | No; a fourth sequence or a new duration would |
| Email or social login with embedded wallets | Wallet layer behind one interface (§9.2) | No, but the custody model must be reviewed |
| Gas sponsorship or meta-transactions | `buy` and `withdraw` bind to msg.sender | Yes; V4 and P9 must be re-proven |

| Referral, loyalty or leaderboard rewards | Indexer attribution and per-asset leaderboard | Off-chain payouts from treasury: no; an on-chain fee split: yes |
| Result notifications | Event stream and API | No; opt-in service under the §9.7 privacy rules |
