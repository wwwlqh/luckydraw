# LuckyDraw v8 — Acceptance and release evidence

The rules are in `SPEC.md`; this file maps them to observable acceptance. All contract/app/operational rows start **not run** until actual evidence is recorded. Mathematical reference checks do not satisfy deployment or security gates. Use this document as the implementation checklist and update evidence links alongside the code.

## Required scale and operational evidence

- Foundry campaign: at least 100,000 recorded non-reverting handler actions across assets/kinds/users with reverted calls at or below 20%, V1–V5/D1–D6/D8–D10 checked after each; handler calls that make no protocol call for want of an eligible target are counted and published separately and are not part of that ratio; publish runs, depth, seeds, per-action-type counts and minimized failures.
- Progress: each D7 scenario records time steps, caller and VRF delivery assumption (delivered or never delivered) and the reached state; no scenario asserts Drawing→Ready without a stated delivery assumption.
- Latency and gas: measured cutoff-to-settled p50/p95 on mainnet, first from the shakedown rounds and then over three days of service, included-to-finalized latency, and a gas table for buy (subsequent, first in round and target-closing), closeRound, requestDraw, settle, claimRefund and withdraw against the §11.2 targets under the pinned compiler.
- Static and mutation: Slither triage committed with zero untriaged medium-or-higher findings; mutation campaign report with every surviving mutant reviewed.
- Traceability: `python scripts/trace_check.py` passes (every P/V/D covered; every citation resolves).
- Security review follow-up: the request pre-checks (A42), V5 limits (A43), aggregator bounds (A44) and emitter filtering (A45) have tests before deployment, and the independent review in §14 covers the consumer adapter and the pre-check derivation.
- Callback: <=150,000 measured consumer gas under cold valid cases within the configured 300,000 limit; include zero/nonzero words and actual consumer adapter.
- Settlement: 100,000 purchase ranges plus arithmetic/index bounds analysis; winner lookup never scans all holders. Record actual gas and the mainnet transaction limits.
- Price tests: all 0–18 decimal combinations, exact minimum/freshness thresholds, fake/malicious feeds, stale feed while money exits remain available.
- Keeper: three days of healthy execution, all seven schedule kinds (three daily, three weekly, one monthly — ADR 036) exercised locally with time travel, no starvation, restart without duplicate requests, correct alert destinations and nonce recovery.
- Index: overlapping scans, disconnect/restart, duplicate logs, shallow/deep reorg, pagination consistency and successful full rebuild from deployment.
- Deployment: pinned toolchain/dependency hashes, verified contracts, immutable consumer adaptation reviewed, owner/binding receipts, correct subscription/consumer configuration, local mocks impossible in production manifest. The deploy script asserts the chain id (and that it agrees with the plan's `environment`), the coordinator's `s_provingKeys(bytes32)` and `getSubscription(uint256)` getters, and deployed code at `finalOwner`, `feeAccount` and `seedAccount` outside `local`, before deploying; the configure script asserts the manifest's VRF coordinator, subscription id, key hash and `maxRequestCostNative` against the Draw's immutables, consumer registration and the low-funding threshold before each `addPool`; mock detection compares deployed code with the repository's mock artifacts rather than the manifest's own labels; `Verify` re-checks every recorded fact against live chain state and exits non-zero on any mismatch; `scripts/validate_config.ts` re-checks the manifest against `config/schema`.
- Mainnet: independent contract review with critical/high findings resolved; operator signs residual-risk acceptance; jurisdiction/access requirements resolved. Real deployment is a separate operator action.
