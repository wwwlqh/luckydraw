# LuckyDraw

On-chain lucky draw on BSC: USD 1 reference minimum, no product maximum, seven whole-USD target tiers per pool (daily 100, 1,000 and 10,000; weekly 1,000, 10,000 and 100,000; monthly 100,000 by default) that draw as soon as the target is reached with the fixed UTC daily/weekly/monthly cutoff as the latest draw, 3% deducted on entry, an operator seed entry in every funded pool so a lone player gets a draw instead of a refund, and no deposit/withdrawal platform fee.

`docs/SPEC.md` is the design of record. Read it before changing contracts, the data model or user flows. `docs/ACCEPTANCE.md` maps requirements to evidence. If code and spec disagree, resolve the design and update both together.

Decisions and alternatives are in SPEC.md §13; §12.1 says what is v1 build work versus a mainnet gate (build only the left column first); §17 lists deferred features, unscheduled; historical findings are in REVIEW.md. Reopen a decision with a reason, without silently overriding confirmed user rules.

V1–V5 in §4 and D1–D6 and D8–D10 in §11 require stateful contract invariants. D7 requires progress scenarios with explicit oracle assumptions. `scripts/spec_reference.py` validates independent math examples; it is not a substitute for Solidity, UI, integration tests or an audit. Contract unit, vector, integration, D7 progress, 100,000-range scale and stateful invariant suites exist; the `scale` and `campaign` Foundry profiles and the recorded-campaign procedure are in `contracts/README.md` and the ACCEPTANCE evidence ledger.

Generate `docs/SPEC.html` from Markdown using `python scripts/render_spec.py` (Python Markdown dependency). Do not edit HTML independently. Run `python scripts/spec_reference.py` when changing financial, schedule or selection math; update evidence after actual validation. Both scripts refresh their own fields in `docs/SPEC_CHECKS.json`; do not hand-edit it. `spec_reference.py` also writes `contracts/test/vectors/spec_vectors.json`. Run `python scripts/trace_check.py` after editing SPEC.md or ACCEPTANCE.md. Run `python scripts/check_generated.py` for the read-only CI freshness check; it ignores only the check timestamp. Configuration records live in `config/` and are validated by `scripts/validate_config.ts`: run `pnpm validate:config` and `pnpm test:config` (pnpm 12.3.4 through `npx pnpm@12.3.4 ...` if pnpm is not installed; Node 24 LTS is pinned in `.nvmrc` and 25 also works) after changing anything under `config/` or producing a deployment manifest. The validator needs no network access and reads no secrets; `config/README.md` lists the naming rules and every cross-field rule.

Never handle private keys, seed phrases or RPC secrets in this repo. Deployments are operator-run from `contracts/script/` (Deploy, Configure, Finalize, Verify; DeployLocal for anvil with labeled mocks) after the §14 gates; a manifest lands in `config/deployments/<chainId>/<lowercase draw address>.json` and must pass `Verify` and `pnpm validate:config`. Local/testnet work may proceed with labeled mocks and without mainnet credentials.
